# Отрицательный контроль: инциденты с ИИ в разработке против определения

**Статус:** третья проба определения из `definition.md`. Две калибровки (`calibration-curl.md`, `calibration-sqlite.md`) проверяли, пропускает ли определение хорошее ПО. Эта проверяет обратное: ловит ли оно известные провалы. Для каждого публичного инцидента один вопрос: какой критерий должен был его поймать и есть ли он в определении.

**Оговорка об источниках.** Большинство описаний вторичны: блоги вендоров безопасности, пресса, посты пострадавших. Цифры расходятся между источниками. Инциденты, где первоисточник не найден, помечены «(не подтверждено)». Собрано 2026-10-18 поиском, не чтением первоисточников.

Шкала: **ЛОВИТ** критерий есть и прямо описывает отказ; **ЧАСТИЧНО** критерий есть, но ловит при расширительном толковании или только в надстройке; **ДЫРА** критерия нет.

## 2) Итог по критериям

**Ловят напрямую:** Б2/Б7 (Г1), Б17 (А3, Б6), Б18 (В1), Б19 (Б6). Ядро «артефакты, а не слова» подтверждено самым частым классом инцидентов: ложным отчётом агента.

**Ловит только надстройка:** Н7 и Н3 при внешнем адресате (Б1), Н6 (А1, А3), Н15 (А4, В2). Для потребительских приложений с чужими данными надстройка обязательна по правилу «внешний адресат», значит, определение их ловит, но только если квадрант определён честно.

**Дыры, подтверждённые инцидентами:**

1. **Среда, в которой работает агент.** Четыре из пяти разрушительных инцидентов (А1–А4) произошли не в продукте, а в окружении агента: прод доступен из сессии, секреты в досягаемости, разрушительные команды без подтверждения, бэкапы рядом с данными. Определение описывает ПО и молчит о среде. Для ИИ-разработки это главная дыра.
2. **Негативные тесты авторизации.** Четыре инцидента (Б2, Б3, Б5, частично Б1) это один класс: данные отдаются тому, кому нельзя. Ни SAST, ни конфигурация вне кода, ни валидация ввода этого не ловят. Нужен базовый критерий: для каждого пути к данным есть тест, что чужой получает отказ. Он дёшев и автоматизируем.
3. **Защита проверяющих артефактов.** Г2, Г3: агент правит тест, таймаут или проверяющий скрипт вместо кода. Нужен критерий: изменение тестов, CI-конфига и проверяющих скриптов в одном шаге с проверяемым кодом требует отдельной причины и отдельного взгляда.
4. **Процесс приёма уязвимостей.** Б4, второе подтверждение после curl.
5. **Инструменты агента как зависимости.** В2: Б18 должен распространяться на расширения, CLI и MCP-серверы, которыми работает агент.

**Поправка к выводу из `calibration-curl.md`.** Там буква Б7 «одна команда» названа лишней. Г1 показывает, зачем она нужна: подмена объёма проверки. Переформулировка должна сохранить эффект: «нет способа прогнать часть набора и назвать результат полным».

## 3) Что это меняет в структуре определения

Инциденты делятся на два объекта: **продукт** (группы Б, В) и **процесс с агентом** (группы А, Г). Определение «качественное ПО» честно покрывает первый. Второй требует отдельного раздела, назовём его рабочим именем «Среда агента», с критериями:

- из среды агента недостижимы прод и его учётные данные;
- разрушительные команды проходят через подтверждение или dry-run независимо от режима инструмента;
- бэкапы лежат вне зоны поражения агента и восстановление отрепетировано;
- права токенов агента минимальны для задачи;
- проверяющие артефакты (тесты, CI, скрипты проверки) защищены от правки в том же шаге, что и код;
- инструменты агента прибиты по версии и проверены как зависимости.

Это не критерии ПО, а условия, при которых критерии ПО вообще можно доказать. Без них «артефактами, а не словами» не работает: агент может подменить артефакт.
