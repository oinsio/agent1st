# Прогон кандидатов по девяти калибровкам

**Статус:** записано 2026-10-19. Проверяются девять кандидатов из четырёх разборов этого дня: Н-Перф, Н-Польз, Н-ПДн из `consequence-3-scope.md`; Н-Крипто, Н-Аутент, Н-Инъекции, Н-Угрозы из `owasp-crosscheck.md`; Н-Трасс и тип компонента «под нагрузкой» из `asvs-and-nonfunctional-crosscheck.md`. Фраза для §3 из `postel-law.md` не критерий и не прогонялась.

**Метод.** Восемь сохранённых клонов из прошлых калибровок проверены восемью агентами последовательно, по одному брифу с единой шкалой и обязательным разделом «Трение». Отрицательный контроль по инцидентам прогнан без агента. Факты собраны только чтением клонов; прогоны не запускались. Для GitLab.com код приложения не клонирован, часть фактов взята из raw-файлов по сети. Бриф агентов и их полные отчёты лежат в scratchpad сессии и в репозиторий не входят; здесь сохранены факты с путями.

**Правило чтения вердиктов.** ДА артефакт есть и производит эффект в обвязке; ЧАСТИЧНО эффект частичен, или артефакт не подключён к обвязке, или приватен; НЕТ ничего; Н/П условие включения не выполняется.

## 2) Вердикты по кандидатам

### Н-Перф: оставить, переписать артефакты по типу компонента

Эффект «ухудшение в горячем пути видно до поставки» подтверждён: артефакты встречаются в семи проектах из восьми, и ни один из них не похож на «нагрузочный стенд в CI». Калибровки показали четыре формы одного эффекта:

| Тип компонента | Артефакт | Где найден |
|---|---|---|
| Библиотека | число инструкций CPU и размер бинаря с diff к базе; число соединений на сценарий как тест | SQLite `test/speedtest.tcl` считает инструкции через cachegrind и размер через `size`, сравнение `fossil xdiff`; curl `assert r.total_connects == N` в pytest |
| Сервис с хранилищем | число запросов и план SQL с сравнением к базе | GitLab `QueryRecorder` с матчерами `exceed_query_limit`, лимит 100 запросов на контроллер; `merge_request_query_differ.rb` сравнивает планы между master и MR |
| Поставка приложения | храповик размера артефакта с запретом возврата выброшенного | flutter_agent_harness `scripts/size_manifest.py` +5% на строку и на итог, флаг `--forbid` |
| CLI и TUI | счётчики работы вместо таймингов; архитектурный тест горячего пути | flutter_agent_harness «work counters, not timings — CI-safe»; herdr `test_ui_hot_path_architecture.py` запрещает классы вызовов в горячем пути |

Три уточнения правил зачёта из прогона:

- **Оценка не замер.** Documenso: планы агентов пишут «+1 upsert ~1ms», это оценка. Засчитывается только измеренное.
- **Гейт на релизе с порогом даёт ЧАСТИЧНО.** herdr: `release_perf_smoke.sh` сравнивает CPU кандидата со stable-бинарём с порогом 25%, но запускается только из `just pre-release-check` руками. Не CI, но и не проза.
- **Детерминированная метрика предпочтительнее секунд.** Пять проектов из семи с артефактом выбрали инструкции, байты, число запросов или счётчики. Секунды в обвязке шумят, и проекты это знают.

Условие включения. Gnomish Factory показал, что «сервис под нагрузкой» даёт Н/П, а «внешний адресат» дал бы НЕТ, при том что у проекта есть горячий путь: вызовы GitHub API и стоимость токенов. herdr записал в инструкциях «мультипликативные пути: per byte, event, render × panes × clients». Предлагаемое условие: компонент с горячим путём, где работа множится на кардинальность, или с бюджетом размера поставки.

Трение Documenso «деградация абсорбируется масштабированием» не принимается: масштабирование переводит регрессию в счёт за хостинг, не делает её видимой. Масштабирование относится к оси типа, не к Н-Перф.

### Н-Польз: для CLI и API уточнить Я10 и Я13, новый критерий только для интерфейса

Единственное ДА у curl, и оно получено артефактами, которые уже входят в Я10: примеры из man-страниц компилируются в CI, справочник сверяется с кодом. herdr делает то же со справочником конфигурации, flutter_agent_harness прогоняет установщик через реальный PTY в трёх оболочках и проверяет, что ключ не попал в транскрипт. Для CLI и API кандидат сводится к «документация исполняема обвязкой», и это уточнение Я10 и Я13, а не новый критерий.

Для интерфейса везде ЧАСТИЧНО по одной причине: e2e есть, но идут через фикстуры и прямые вызовы API, а не по пользовательской документации. Documenso: 157 спецификаций через `apiSignin`. Clear Progress: 19 сценариев, включая «первый визит» и «настройка Supabase по README», но Playwright не в CI. Отличительный признак критерия найден: сценарий идёт по тексту, который читает пользователь, а не по знанию автора.

Доступность: только Clear Progress имеет систематические тесты axe с тегами в сценариях, у остальных ноль или один тест. Это Н16, не Н-Польз.

### Н-ПДн: оставить, разделить на два эффекта и переписать условие

Условие «хранит персональные данные» не работает для локального софта: herdr и flutter_agent_harness хранят данные самого пользователя на его машине, субъекта данных, отличного от владельца, нет. Clear Progress: оператор это сам субъект. Предлагаемое условие: данные другого субъекта, или данные уходят с машины.

Прогон разделил кандидат на два эффекта с разными артефактами:

1. **Персональные данные учтены и удаляемы.** Documenso: `delete-user.ts` и девять e2e, проверяющих базу напрямую, включая негативный «неверный email ничего не удаляет». flutter_agent_harness: тест синхронизации `PRIVACY.md` с опубликованной страницей по девяти обязательным секциям магазина. Clear Progress: каскад удаления в схеме на девять таблиц, но без каскада файлов. Поправка Documenso: для юридически значимых документов удаление по сроку противоречит законам о хранении записей, поэтому «хранить бессрочно по закону» это валидная политика.
2. **Чувствительное не попадает в логи, транскрипты и постоянное хранилище.** Этот эффект нужен и там, где нет персональных данных: curl маскирует секреты в трассе кодом и тестирует утечку учётных данных при редиректах; herdr пишет сырые байты ввода, включая пароли, в debug-лог без теста; GitLab фильтрует параметры логов с комментарием «labkit filter must be updated whenever this list changes» и без теста согласованности; flutter_agent_harness имеет пайплайн редактирования, но слой персональных данных выключен по умолчанию, что само есть нарушение Я17. Ни в одном из девяти проектов нет теста «в логах нет email»; тест на отсутствие токена в логах есть у одного, Gnomish Factory (`GithubTokenHygieneSpec`, ADR 0004 «ни одного секрета в строке лога»), и в первой редакции этой сводки был пропущен; поправлено при прогоне v2.1. Это отдельный критерий с условием «обрабатывает учётные данные или персональные данные», и отрицательный контроль его подтверждает: Б1 Tea, фото документов хранились после обещанного удаления, и Б6, 175 случаев персональных данных в открытом виде, ловятся им точнее, чем Я21.

### Н-Крипто: оставить, сузить и заменить артефакт по умолчанию

Линтера на слабые примитивы нет ни в одном из восьми проектов. Артефакт по умолчанию надо менять. Что реально встречается:

- пароли через bcrypt у единственного проекта со своей аутентификацией, Documenso;
- ключевой материал через внешний транспорт: Documenso поддерживает p12, Google Cloud HSM и CSC; GitLab тянет секреты из Vault через External Secrets с версиями ключей в манифестах; Gnomish Factory отказывается читать файл секретов с широкими POSIX-правами и тестирует это;
- клиентские опции транспорта прибиты и протестированы: herdr `StrictHostKeyChecking=yes` в argv с тестом; curl дефолт TLS 1.2 в коде, SSLv2 и SSLv3 отвергаются.

Два отрицательных образца: Documenso, валидация ключей шифрования написана и закомментирована; flutter_agent_harness, при отказе `Random.secure()` код молча падает на `Random()` для PKCE, что есть «отказ в заглушку» из Я5, и `disableHostkeyVerification: true` для SSH.

Сужение по SQLite: «своих примитивов нет» наказывает библиотеку без зависимостей за ChaCha20 для случайности и урезанный SHA3 для некриптографического сравнения. Формулировка: «примитивы для конфиденциальности и аутентичности не самодельные».

### Н-Аутент: переписать через эффект, разбить на три подпункта

Самая сильная находка прогона у herdr: доступ ограничен идентичностью процесса в ОС, сокеты 0600 с тестами, и интеграционный тест на Windows создаёт реальный процесс с пониженными правами и ждёт отказа. По формулировке кандидата Н/П, по эффекту ДА. Критерий должен быть записан через эффект, как все остальные: «доступ ограничен идентичностью, и чужая идентичность получает отказ в негативном тесте».

Три подпункта для подсчёта, по Documenso, где два из трёх покрыты тестами, а третий отключён:

1. **Перебор ограничен, и лимит не отключён в прогоне.** Documenso: лимиты входа 10 за 15 минут на IP в Postgres между инстансами, но в e2e выставлено `DANGEROUS_BYPASS_RATE_LIMITS: 'true'`, обход зашит в код, а спецификация лимитов сама себя пропускает при этом флаге. Правило 2 из §3 в чистом виде.
2. **Сессия или токен гаснет при выходе и смене секрета.** Documenso: `invalidateSessions` при смене и сбросе пароля с e2e-тестами «password reset invalidates all sessions» и «update keeps current». Clear Progress: тесты на `SIGNED_OUT` и принудительный выход после серии 401.
3. **Учётных данных по умолчанию нет.** Documenso: `password = 'password'` только в seed для разработки.

Два расширения, без которых критерий не получит ДА на половине проектов:

- **Делегированная аутентификация** (Clear Progress, GoTrue): засчитываются конфигурация провайдера в репозитории, тест реакции клиента на отказ, серверная проверка токена в каждом входе.
- **Клиентская сторона** (flutter_agent_harness, Gnomish Factory): для OAuth-клиентов PKCE, state и хранение refresh-токенов; для клиентов API отказ от запроса учётных данных и маскирование.

Артефакт в «что искать»: Documenso `UserSecurityAuditLog` с событиями `SIGN_IN_FAIL`, `SESSION_REVOKED` и прочими как машинный инвентарь событий безопасности.

### Н-Инъекции: разделить на три по типу компонента

Один вердикт на два разных эффекта не информативен, об этом сказали пять агентов из восьми. По калибровкам:

| Тип компонента | Эффект | Артефакты | Где найден |
|---|---|---|---|
| Потребитель хранилища и команд | запросы строятся не конкатенацией | параметризация как единственный путь плюс тест изоляции; SAST как замена, не умолчание | Clear Progress: единственный путь к базе через plpgsql без `EXECUTE`, RLS, тесты изоляции и cross-tenant; Documenso: Prisma, пять `$queryRaw` все параметризованы; Gnomish Factory: типизированный недоверенный ввод с архитектурными гейтами |
| Парсер недоверенного ввода | парсер не десинхронизируется и не переполняется | фаззинг грамматики с инвариантами; пределы размера на каждом входе с тестом восстановления | SQLite `fuzzinvariants.c`, корпуса в `releasetest`, лимиты глубины парсера; herdr `MAX_FRAME_SIZE` и тесты «oversized discarded and recovers»; curl запрет небезопасных строковых функций линтером и тесты CRLF-инъекций |
| Агентная система | недоверенный контент изолирован, опасные действия проходят подтверждение | карантин контента, перехватчик команд, песочница | flutter_agent_harness `quarantine.dart`, `approval.dart`, песочница. Это уже Н17, новый критерий не нужен |

SAST найден у трёх проектов и работает у двух: Gnomish Factory CodeQL плюс Error Prone, curl CodeQL плюс checksrc. У flutter_agent_harness файл CodeQL лежит вне каталога workflows и не исполняется, а Dart CodeQL не поддерживает. У GitLab собственные правила Semgrep запускаются с `|| true`, результат не влияет на статус. Это породило новое правило зачёта, см. §3.

### Н-Угрозы и Н-Трасс: слить в один критерий

Все восемь агентов независимо сказали, что эти два кандидата неотличимы на их проекте. Н-Угрозы не получил ни одного ДА. Единственное ДА по Н-Трасс у Gnomish Factory: гейт `checkSpecContract` в составе `./gradlew check` ломает сборку, если сценарий спецификации не назван маркером в тесте или наоборот, исключения лежат в данных, и требования безопасности NFR-S1, S2, S3 в нём обычные требования. Это и есть форма критерия, предложенная в сверке с ASVS: безопасность вводится через трассировку, стандарт становится источником требований.

Слитый критерий: «Требования безопасности и угрозы записаны, каждая запись связана с проверкой, и связь проверяется обвязкой». Уточнения из прогона:

- **Транзитивная цепочка принимается, если каждое звено проверяется машиной.** Gnomish Factory: реестр угроз ссылается на изменение, изменение на сценарии, сценарии на тесты через гейт. Без гейта на каждом звене это ЧАСТИЧНО.
- **Отрицательная половина модели дёшева и проверяема по инцидентам.** curl `VULN-DISCLOSURE-POLICY.md` перечисляет, что не считается уязвимостью. flutter_agent_harness записывает «принятый остаток» у угрозы.
- **Внешняя сертификация приватна и даёт ЧАСТИЧНО.** Documenso SOC 2 на trust-портале; GitLab контроли в handbook. Это согласуется с §8 и менять его не нужно.
- **Реестр без документа.** Documenso: таблица лимитов с тирами «отправляет письма, неаутентифицирован, проверяет секреты» это неназванный реестр угроз по эндпоинтам. SQLite: угрозы живут как флаги API с комментарием «attacker» и тестами, грепающими флаг. Засчитывается, если grep по контрмере даёт тест.

Четыре кандидата из сверки с Top 10 остаются минимумом для проекта без выбранного стандарта.

### Тип «под нагрузкой»: оставить как ось, признак работает

Признак «один экземпляр не справляется или цена простоя записана» дал правильный ответ на всех девяти: отрицательный на шести, положительный на Documenso и GitLab. Артефакты признака, которых не было в брифе: автоскейл с минимумом и максимумом (Documenso HPA 2 до 10 в документации Kubernetes, GitLab HPA api 25 до 450), распределённые лимиты между инстансами, реплики чтения, прогноз насыщения (GitLab capacityPlanning в каталоге метрик и Tamland).

Две находки за пределами оси:

- **Репетиция отказа экземпляра есть и без нагрузки.** Gnomish Factory масштабируется горизонтально ради отказоустойчивости, не нагрузки: claim-lease, heartbeat, reaper, и тесты killpoint, TakeDeathAndRecovery, ServeRestart. Дополнение к Н4 «отказ экземпляра отрепетирован» нужно вне зависимости от оси.
- **Для однопользовательского инструмента замена оси это записанные кардинальности.** herdr: пределы 1, 15, 50 панелей, мультипликативные пути в инструкциях агенту, тесты честности очереди. Это Н15 «известные пределы измерены», не новый критерий.

## 3) Сквозные находки прогона

### 3.1 Новое правило зачёта: проверка, не подключённая к исполнителю

Один паттерн повторился в шести проектах: артефакт есть, эффекта нет, и grep его не отличает от работающего.

| Проект | Факт |
|---|---|
| flutter_agent_harness | `.github/codeql.yml` вне `workflows/`, не исполняется; `perf-gate` под условием `pull_request` при CI только по ручному запуску, в комментарии признано «permanently skipped» |
| Documenso | валидация ключей написана и закомментирована; лимиты обходятся флагом в CI, тест сам себя пропускает; Vitest не запускает ни один workflow; Dependabot указывает на несуществующий каталог с нулевым лимитом |
| GitLab | собственные правила Semgrep с `\|\| true`; SAST отключается стандартными переменными шаблона |
| Clear Progress | e2e, доступность, интеграция и мутации есть, в CI только lint, типы и unit; тест изоляции `describe.skip` без пяти переменных окружения |
| Gnomish Factory | Docker-тесты контрмер имеют «Docker-absent skip path», по тексту workflow не определить, есть ли Docker в CI |
| herdr | перф-гейт только в ручном шаге перед релизом |

Правило 7 для §3: «Проверка, не подключённая к исполнителю, с мёртвым условием запуска, самопропуском по окружению или результатом, не влияющим на статус, не является проверкой». Это расширение правила 2, и оно нужно, потому что правило 2 говорит только о флаге.

Уточнение GitLab к правилу 2 принимается: флаг-отключатель снижает вердикт, только если видно, что он выставлен в канонической обвязке, или если результат не влияет на статус. Существование переменной `SAST_DISABLED` в шаблоне само по себе не отключение. Исключение по образцу GitLab `QueryLimiting.disable!`: отключение, требующее ссылку на issue и новый конечный порог, это не «один флаг», а артефакт долга.

### 3.2 Модификатор «не в CI» как один факт

Clear Progress: один факт «e2e не в обвязке» ограничил сверху семь вердиктов из девяти. Повторять его в каждой строке калибровки неинформативно. Предложение для формата калибровок: отдельная строка «что не подключено к обвязке» перед таблицей, и ссылка на неё из вердиктов.

### 3.3 Вердикт по компоненту, не по проекту

flutter_agent_harness это четыре продукта в одном репозитории: у CLI перф-гейты есть, у приложения только размер. Один вердикт на проект теряет это. §9 уже говорит «для компонента: квадрант», калибровки должны этому следовать.

### 3.4 Градация приватного для библиотечного профиля

SQLite: маркеры требований `EVIDENCE-OF` встречаются 775 раз в открытых тестах, инструмент их сверки приватен. Правило «приватное даёт ЧАСТИЧНО» делает такой проект неотличимым от проекта без ничего. Предложение в §8: различать «приватно, но следы в открытом коде верифицируемы» и «приватно и следов нет». Открытый вопрос.

### 3.5 Отрицательный контроль неполон

В наборе инцидентов нет ни одного про производительность, нагрузку или удобство. Н-Перф, Н-Польз и ось нагрузки отрицательным контролем не проверены. Три инцидента ловятся кандидатами точнее существующих критериев: Б1 Tea и Б6 Escape через учёт персональных данных, Б5 Base44 через аутентификацию, которую Я21 ловил натяжкой.

### 3.6 Трение самого прогона

- Бриф с перечнем «особо интересных» пунктов агент GitLab принял за объём задания и пропустил Н-Польз. Обязательный объём надо перечислять явно, подсказки отдельно.
- Handbook GitLab через загрузку страницы нечитаем: двести килобайт навигации на страницу. Для продуктовых профилей нужны выгрузки Markdown заранее.
- Для продукта с кодом в другом репозитории десять raw-запросов мало: два пути вернули 404.

| Кандидат | Решение |

| Н-Перф | оставить; артефакты по типу компонента; условие «горячий путь с кардинальностью или бюджет размера»; оценка не замер; релизный гейт даёт ЧАСТИЧНО |
| Н-Польз | для CLI и API уточнение Я10 и Я13 «документация исполняема обвязкой»; новый критерий только для интерфейса с признаком «по тексту для пользователя, не по фикстурам» |
| Н-ПДн | разделить: «учтены и удаляемы» с условием «данные другого субъекта или уходят с машины»; «чувствительное не в логах и транскриптах» с условием «обрабатывает учётные или персональные данные» |

| Н-Аутент | переписать через эффект «доступ ограничен идентичностью, чужая получает отказ»; три подпункта; делегированная и клиентская стороны |
