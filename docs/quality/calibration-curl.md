# Калибровка определения на curl

**Статус:** первая проба определения из `definition.md` на реальном проекте. Цель не оценить curl, а проверить, что определение измеряет качество. curl выбран как проект, чьё качество признано индустрией: 25+ лет, миллиарды установок, публичный процесс.

**Источник фактов:** клон `github.com/curl/curl`, коммит `18c48e0` (2026-10-18), глубина истории 300 коммитов. Всё, что не видно в репозитории, помечено «вне репо».

Шкала: **ДА** артефакт есть и проверяется; **ЧАСТИЧНО** дух соблюдён, буква нет; **НЕТ** артефакта нет; **Н/П** неприменимо; **?** не проверено.

## 3) Что curl делает, а определение не видит

- **Фаззинг как постоянный процесс.** В определении нет ни слова. Для парсеров и сетевого кода это основной способ находить дефекты, сильнее мутационного тестирования.
- **Инъекция отказов аллокации** (torture). Определение относит fault injection в надстройку для «необратимых релизов»; curl держит это в базе для библиотеки.
- **Пределы сложности и длины функций** в CI. Определение не содержит критерия сложности вообще.
- **Процесс приёма и раскрытия уязвимостей:** `SECURITY.md`, `BUG-BOUNTY.md`, `SECURITY-ADVISORY.md`. Свойство Д говорит о секретах, зависимостях и сканировании, но не о том, что делать, когда уязвимость нашли. Это пробел Д.
- **Честные списки незакрытого:** `KNOWN_BUGS.md`, `TODO.md`, `EXPERIMENTAL.md`. Определение требует документацию, соответствующую коду, но не требует документировать то, чего код не делает.
- **Политика ИИ-вклада** как часть процесса, а не трейлер в коммите.
- **Матрица платформ и сборок.** Единый «CI с нуля зелёный» у curl это десятки конфигураций; определение считает одну.

## 4) Выводы для определения

1. **Определение в текущем виде не измеряет качество.** Проект с общепризнанным качеством не проходит базу по шести пунктам. Либо curl некачественный, либо шесть пунктов не базовые или сформулированы неверно. Второе.
2. **Пункты, которые провалились из-за формулировки, а не по сути:** Б1 (нет заказчика), Б7 (три команды вместо одной), Б8 (глоссарий как артефакт), Б16 (передача происходит, но не фиксируется), Б18 (lockfile). Их нужно переформулировать через наблюдаемый эффект, а не через конкретный артефакт.
3. **Пункты, которые провалились по сути, и curl от этого не страдает:** Б12 (дубли), Б13 (ациклические зависимости). Их базовость не подтверждена. Кандидаты на перенос в надстройку с условием «слоистая архитектура, больше N модулей».
4. **Артефакты вне репозитория** (GitHub secret scanning, OSS-Fuzz, curl.se dashboard, ревью в PR) встречаются в пяти пунктах. Определение должно решить: засчитывать с ссылкой или требовать копии в репо. Предложение: засчитывать, если артефакт публично доступен и указан в репозитории.
5. **Б6 нужно сузить.** Молчаливая перезапись `-o` это документированное умолчание, принятое пользователями. Критерий должен бить по неожиданной разрушительности, а не по любой.
6. **Пробелы определения, подтверждённые curl:** фаззинг, сложность кода, процесс обработки уязвимостей, документирование незакрытого. Первые три стоит добавить, четвёртое расширяет Б11.
7. **Предсказание критики подтвердилось:** Б21 смешивает учёт и чистоту; curl делает лицензии автоматически и строго, а учёт модели решает политикой.

## 5) Ограничения этой пробы

- История 300 коммитов, не вся. Б17 по полной истории не проверялся.
- Б5 не проверен: нет инструмента.
- Один проект, один тип (библиотека плюс CLI на C). Сервис с данными и UI проверит Г и Н6, Н11, Н14 иначе. Следующий кандидат для калибровки должен быть веб-сервисом.
