# Калибровка определения v1 на Clear Progress

**Статус:** четвёртая проба, первая по версии 1 определения (`definition.md`, коды Я/К/Н/С) и первая на проекте, написанном с ИИ. Clear Progress это PWA для задач и целей: монорепо из пяти пакетов на TypeScript, клиент-first с IndexedDB, синхронизация через Supabase, разработка по OpenSpec с Claude Code. Проект без внешнего признания, что и нужно: предыдущие две калибровки проверяли, не отвергает ли определение хорошее; эта проверяет, различает ли оно обычное.

**Источник фактов:** клон `github.com/oinsio/clear-progress`, коммит `a2bd063` (2026-08-07), полная история: 551 коммит с 2026-03-05, один автор. Объём: 462 файла unit-тестов, 229 feature-файлов, 19 из них e2e, 118 архивных изменений OpenSpec, 87 стабильных спецификаций, 3 глобальных ADR.

**Квадрант:** внешний адресат (публичное приложение, чужие персональные данные), релиз умеренно обратим (статический хостинг, данные у пользователя в IndexedDB и в его собственном Supabase). Тип компонента: хранит данные, парсит внешний ввод. Надстройка обязательна почти целиком.

Шкала: ДА / ЧАСТИЧНО / НЕТ / Н/П.

## 5) Что это говорит об определении

1. **Определение различает.** curl и SQLite прошли ядро на 7–9 ДА из 22 по старой шкале, Clear Progress на 8 из 21 по новой, но с другим профилем: у него сильны процессные артефакты (Я1, Я11, Я12, К5), слабы верификационные (Я7, К1, К2) и среда (С). Определение видит, где именно проект держится на дисциплине агента, а не на доказательствах.
2. **Слой компенсации подтверждён положительно.** Три риска, под которые он написан, реализовались в одном проекте и найдены вручную: дублирование (К4), мёртвый код (Я9), маскирование ошибок (Я5). curl и SQLite не делают проверку дублей и не страдают; проект с ИИ не делает её и страдает. Это ровно то разделение, ради которого ядро отделено от компенсации.
3. **Я1 показывает, что фиксированная цена обвязки с агентами падает.** Трассировка «требование → тест» на 1109 тегах была бы неподъёмной для трёх разработчиков SQLite и стоит почти ничего в процессе OpenSpec. Аргумент из критики v0 получил пример.
4. **Новый паттерн для К1: доказательство создаёт обвязка.** Хук, запускающий тесты после каждого редактирования, это артефакт, который агент не может подменить отчётом. Стоит записать как артефакт по умолчанию для К1. Обратный пример в том же проекте: отчёт о мутациях, написанный словами, потому что агенту запрещён прогон.
5. **К2 и С5 нужны именно здесь.** Проект защитил спецификации от правки (архив неизменяем), но не тесты. Это половина правильной идеи. Определение должно явно расширять неизменяемость на проверяющие артефакты.
6. **Четвёртый профиль доказательств: самостоятельный хостинг.** Пользователь сам поднимает бэкенд. Эксплуатация (Г) и бэкап (Н6) переходят к нему, но определение этого не предусматривает. Для такого продукта артефакты Г это инструменты и инструкции пользователю: экспорт, проверка восстановления, список того, что сломается при обновлении схемы.
7. **Команда из одного человека и агентов.** Н7 (независимый ревьюер) и К8 (прочитано человеком) при одном авторе вырождаются. Определение должно сказать, что считается: второй агент без доступа к рассуждениям первого удовлетворяет Н7, а К8 закрывается порогом мутаций, если чтения нет.
8. **С1 реализовалось без инцидента.** Токен прода в рабочей директории агента, деплой миграций оттуда же. Инцидента не было, предусловие есть. Отрицательный контроль предсказал ровно это.

## 6) Ограничения

- Один проект одного автора, который одновременно сопровождающий этого исследования. Оценка не независима.
- Интеграционные и e2e-прогоны не запускались; вердикты по ним основаны на наличии артефактов, не на зелёном прогоне.
- Фактический мутационный счёт известен только из собственного отчёта проекта по четырём файлам.
