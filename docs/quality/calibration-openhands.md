# Калибровка определения v3.0 на OpenHands (Agent Canvas и software-agent-sdk)

**Статус:** двенадцатая проба, третья по версии 3.0, первая на продукте «агент с действиями» для внешнего адресата. Записана 2026-10-19. Репозитории только читались: ни установка, ни тесты, ни скрипты не запускались; это решение сопровождающего после инцидента LiteLLM и кампании TrapDoor, целившейся в файлы инструкций агентам именно этого проекта.

**Что это.** OpenHands разделён на репозитории с записанными границами владения. `OpenHands/OpenHands` это Agent Canvas: интерфейс на React и TypeScript, пакет npm `@openhands/agent-canvas` 1.28.1, образ Docker, чарт Helm, настольное приложение на Electron; 1151 файл `.ts` и 1086 `.tsx`, 873 файла тестов с 7725 проверками, 31 сценарий Playwright. `OpenHands/software-agent-sdk` это Python SDK и Agent Server: агент, инструменты, песочницы, анализаторы безопасности, REST и WebSocket; 519 файлов, 137 407 строк, 776 файлов тестов с 9898 проверками. Canvas не исполняет действия агента и не хранит учётные данные провайдеров; это записано в `docs/architecture.md` и `AGENTS.md` обоих репозиториев. 91 271 звезда, MIT.

**Почему он:** §10 определения называл абзац «вызывает LLM» и Н19 не проверенными практикой на продукте с действиями и внешним адресатом; herdr и Gnomish Factory были инструментами для себя. Из кандидатов (Pydantic, LiteLLM, OpenHands) это единственный с ярусами риска, политиками подтверждения и анализаторами безопасности в коде.

**Источники фактов:** клоны `main` одним коммитом: Canvas `8d39305` (2026-10-19, 42 МБ), SDK `33d8aa2` (2026-10-19, 32 МБ). GitHub API без авторизации: 100 последних коммитов каждого репозитория (оба за 2026-10-13..19), правила ветки `main` Canvas, ревью на четырёх запросах Canvas, тело одного запроса, профиль сообщества. Вне репозитория: реестр npm (провенанс 1.28.1), PyPI (провенанс `openhands-sdk` 1.56.0), база advisories GitHub и GitLab, отчёты о кампании TrapDoor. Scorecard для нового имени организации не отвечает. Прогоны не запускались.

**Авторство.** Canvas: один сопровождающий даёт 62 коммита из 100, `all-hands-bot` 6, `openhands-release-bot` 2; все 100 это слитые запросы с номером и заголовком conventional commits. В завершающих строках коммитов: `Co-authored-by: Claude Opus 5.5` 20 раз, `Claude` 4, `openhands` 13. SDK: тот же сопровождающий 71 из 100, `Co-authored-by: Claude` 30, `openhands` 21, `Claude Opus 5.5` 3. Это первая проба, где модель названа в завершающей строке коммита.

**Профиль и уровень.** Библиотечный (пакет npm, SDK на PyPI) и самостоятельный хостинг (`docs/SELF_HOSTING.md`, Docker, Helm); облачный профиль не оценивался. Внешний адресат. Релиз Canvas обратим: npm и теги образов, старая версия доступна; у SDK миграции настроек с золотыми фикстурами. Типы: вызывает LLM с действиями и с недоверенными источниками в контексте (репозиторий пользователя, страницы браузера, MCP), хранит данные (беседы и ключи бэкендов в `localStorage` и каталоге состояния), работает непрерывно (сервер), парсит внешний ввод (вывод модели, markdown). Под нагрузкой: признака нет. Код агента: по завершающим строкам коммитов большая часть изменений, компенсация обязательна. Н27: Canvas и Agent Server назначены на один уровень, граница между ними это сетевой API с ключом сессии; не проверялась.

**Не подключено к обвязке (§9 п.8).** Canvas: правило ветки требует одну проверку, `test-and-build (ubuntu)`: линт, типы, модульные тесты, сборка, сборка библиотеки, `npm pack --dry-run`; сборка на Windows без проверок. Сквозные сценарии с двойником модели (`mock-llm-e2e.yml`) идут только при отправке в `main`, не на запросе; живые сквозные сценарии в `ci.yml` пропускают себя без `LLM_API_KEY` и на запросах из форков (правило 7); сборка образа с дымовой проверкой идёт на запросе, но не обязательна; мутации Stryker и `scripts/stryker-diff.mjs` в обвязке не вызываются; `npm run check-translation-completeness` только в `lint-staged`; Playwright на CI с `retries: 2`. SDK: `--cov-fail-under=0`; `run-examples.yml` только по метке `test-examples`; `check-documented-examples.yml` с `continue-on-error`; правила ветки SDK публике не видны.

Шкала §3: ДА / ЧАСТИЧНО / НЕТ / Н/П. Где компоненты расходятся, вердикт записан по каждому.

## 5) Что это говорит об определении

1. **Абзац «вызывает LLM» и Н19 впервые проверены на продукте.** Все названные в нём механизмы найдены: ярусы инструментов, подтверждение, аварийный выключатель, бюджеты токенов и итераций, повреждённый ответ модели в тестах, редактирование транскриптов. Чего нет, так это корпуса инъекций с проверкой «действие не произошло», и это ровно артефакт, который Н19 ставит по умолчанию. Строка Н19 различает механизм и доказательство правильно.

2. **Защитный слой, выключенный по умолчанию, ловится через Я17, а не через Я6.** Я6 видит механизмы и склонен к ДА; НЕТ-сторону несёт фраза Я17 «защитный слой, выключенный по умолчанию, это небезопасное умолчание». Стоит добавить в строку Я6 для ветви «модель с действиями» отсылку: умолчание политики подтверждения оценивается по Я17.

3. **К1 получил артефакт против штампа.** `check_approval_drift.py` требует одобрение человека и совпадение проверенного дерева со слитым; LiteLLM показал, зачем это нужно (бот-штамп). Кандидат в артефакты К1 и Н9: «проверка, что последнее одобрение человека относится к слитому дереву».

4. **К2 и С5 нашли форму защищённого пути без файла владельцев.** Изоляция навыков проверки: отдельный запрос, отдельный контекст, workflow на `pull_request_target`, который не исполняет код запроса, с тестом самого workflow. Строка С5 говорит «через владельца пути»; здесь владелец заменён процессом и проверкой. Это замена, которую стоит назвать: «отдельный запрос, проваливаемый обвязкой при смешении с продуктовым кодом».

5. **К7 подтверждён дважды.** `exclude-newer = "7 days"` в `uv` и `cooldown` Dependabot это минимальный возраст; `check_dependency_diff.py` это проверка разницы lockfile. После Pydantic это второй проект с возрастом и первый с разницей lockfile. Оба артефакта у SDK на релизе, не на попытке; строка К7 говорит «до установки», и здесь разрыв между формулировкой и практикой.

6. **К8 нашёл модель в коммите.** `Co-authored-by: Claude Opus 5.5` это первый случай учёта модели по строке К8. Слабое место: строка ставится самим агентом и не проверяется линтером, коммит без неё неотличим от человеческого. К8 требует проверку исполнения обвязкой, и здесь её нет.

7. **Н4 получил эталонный артефакт и не засчитал его целиком.** Навык `verify-openhands` это агент, ведущий приложение как пользователь, с картой, доказательствами и исполняемыми известными дефектами. Строка Н4 требует проход «по тексту, который читает пользователь» без доступа к репозиторию. Сопровождающему решить, достаточно ли карты функций, написанной для агента, как замены пользовательской документации; рекомендация: засчитывать как замену, если карта опубликована пользователю.

8. **Раздел `HUMAN:` это артефакт ответственности, которого нет в К8.** Обвязка требует текст человека и галочку «человек проверил», агенту запрещено его трогать. Кандидат в К8: «поле описания, доступное только человеку, с проверкой обвязки».

9. **Правило 7 отработало на сквозных сценариях.** Три набора Playwright, два из которых не идут на запросе, один пропускает себя без ключа. Без строки §9 п.8 Я2 и Я7 выглядели бы как ДА.

10. **Разделение на репозитории с записанным владением** это артефакт для К4 и К6, которого в строках нет: таблица «репозиторий, что владеет, когда добавлять код туда» снимает дрейф понятий между компонентами. Кандидат в К6.
