# Agent1st как один из источников: что переносится на свойства продукта

**Статус:** эксперимент в стадии рассуждения. Исследование независимое: Agent1st здесь не рамка, а один источник наравне с ISO 25010, DORA, OWASP и эмпирическими работами. Результат может быть применён к Agent1st, а может нет.

**Вопрос:** есть ли в Agent1st что-то, что добавляет к пониманию, каким должно быть качественное программное обеспечение?

**Метод:** Agent1st описывает *процесс* совместной работы, а мы описываем *продукт*. Поэтому для каждого принципа проверяем: переводится ли он из свойства процесса в проверяемое свойство продукта, и есть ли этому внешнее подтверждение. Принцип, который не переводится, не берём.

---

## 1) Разбор по принципам

| Принцип | Свойство процесса | Переводится в свойство продукта? | Внешнее подтверждение |
|---|---|---|---|
| Attention Engineering | внимание агента конечно; важное рядом с точкой решения; шум убран | **да**: локальность ограничений и минимализм кода | дефекты от мёртвого кода и неиспользуемых функций; context rot |
| Semantic Hygiene | одно понятие, одно имя | **да**, и шире, чем в ISO: сквозная согласованность имён код → API → БД → UI → документация | полные слова лучше для понимания и поиска дефектов; похожие имена ведут к ошибкам |
| CDD | трение не обходят молча, а называют | **да**, в зеркальном виде: продукт не скрывает свои сбои, нет тихих обходов | Dummy Handler и Generic Catch сильнее всего связаны с пострелизными дефектами |
| Delegation Design | контракт на границе; ответ с доказательствами и ограничениями | **да**: границы компонентов имеют явный контракт и честно сообщают частичный результат | стандарты безопасности требуют явных интерфейсов для изоляции; практика API |
| Semantic Logging | логи как будущий контекст | **да**, уже в критериях (п. 7) | консенсус практиков SRE |
| Durable State | проект знает то, что знал разговор; не хранить устаревшее | **да**: документация актуальна или её нет; устаревшая запись это дефект | изменения с несогласованными комментариями в 1,5 раза чаще вносят баг |
| Why1st (цепочка требование → решение → контракт → валидатор) | трассируемость проверяется механически | **да**, уже в критериях (п. 1, 29) | — (практика проекта) |
| «Done is not a mood» / доказательства вместо утверждений | | уже базовое правило всего исследования | — |

## 2) Что Agent1st добавляет к классическим спискам

Пять свойств продукта, которых нет в ISO 25010, в чеклистах SRE и в OWASP, или они там размыты.

### 2.1 Локальность ограничений
Инвариант, который нельзя нарушать, записан рядом с кодом, который может его нарушить, а не в документе на другом конце репозитория. Проверка типа, assert, комментарий у точки решения, тест рядом с модулем.
- Откуда: Attention Engineering, «критичные ограничения видны рядом с точкой решения».
- Подтверждение: Lost in the Middle и Context Rot для агентов; для людей косвенно через работы о понимании кода. Для человека это удобство, для агента, который читает только часть репозитория, это условие корректности.
- Чего нет в классике: ISO говорит об «анализируемости», но не о том, *где* должно лежать знание.

### 2.2 Минимализм: нет кода, который не меняет поведение
Нет мёртвого кода, нет функций «на будущее», нет абстракций с одной реализацией.
- Откуда: Attention Engineering, «убрать то, что не меняет решение»; принцип дельта-слоя.
- Подтверждение: до 16% методов в Java-приложениях мёртвые; разработчики тратят время на правку мёртвых методов; мёртвый код ухудшает понимание в контролируемых экспериментах и поддерживаемость на незнакомом коде; 28–45% функций в промышленных системах никогда не используются, и это удивляет самих заказчиков.
- Остро для ИИ: модели добавляют обработку случаев, которых нет, параметры «на всякий случай» и слои абстракции без второй реализации.

### 2.3 Сквозная согласованность имён
Одно понятие названо одинаково во всех поверхностях: код, схема данных, API, интерфейс пользователя, документация, логи. Разные понятия не делят имя.
- Откуда: Semantic Hygiene.
- Подтверждение: полные слова в идентификаторах улучшают понимание и поиск дефектов (эксперимент с профессиональными разработчиками); похожие имена ведут к путанице даже если каждое читаемо само по себе.
- Чего нет в классике: ISO и чеклисты говорят о именовании внутри кода. Расхождение между полем в API и подписью в UI никто не считает дефектом. Для агента это коллизия смыслов, и он правит не то.

### 2.4 Нет тихих обходов
Сбой, откат к запасному поведению или деградация всегда видны: в логе, в метрике, в ответе. Нет `catch` без обработки, нет возврата значения по умолчанию при ошибке без следа, нет «попробуем ещё раз» без счётчика.
- Откуда: CDD, «обход без жалобы скрывает долг процесса». В зеркале для продукта: обход без следа скрывает долг системы.
- Подтверждение: исследование 2018 года на трёх проектах Java и C#: из 17 анти-паттернов обработки исключений сильнее всего с пострелизными дефектами связаны Dummy Handler (пустой обработчик) и Generic Catch; 124 из 357 найденных запахов обработки исключений подтверждены как баги надёжности.
- Остро для ИИ: `try/except: pass` и широкий `catch` одна из самых частых конструкций в сгенерированном коде, потому что она убирает красный тест.

### 2.5 Актуальность как свойство, устаревание как дефект
Документация, комментарии, схемы либо соответствуют коду, либо удалены. Устаревший текст хуже отсутствующего.
- Откуда: Durable State, «обновляй состояние, когда меняется реальность; не храни устаревшие выводы».
- Подтверждение: изменения кода с несогласованным комментарием примерно в 1,5 раза чаще становятся коммитом, вносящим баг, и эффект максимален сразу после появления рассогласования; старые работы на Linux, Mozilla, FreeBSD, PostgreSQL связывают необновлённые комментарии с будущими дефектами.
- Остро для ИИ: агент читает комментарий как правду. Человек может заподозрить, что комментарий устарел; модель почти никогда.

### 2.6 Честная граница
Компонент сообщает частичный успех как частичный, не маскирует ошибку зависимости под свой успех, и его контракт записан там, где его читают вызывающие.
- Откуда: Delegation Design, «возвращай доказательства, ограничения и реальное положение дел, а не уверенный ответ».
- Подтверждение: косвенное, через требование явных интерфейсов для изоляции ошибок в стандартах безопасности (см. `alternatives-to-quadrants.md` §2.3).
- Это же условие делает законной двухслойную модель из `alternatives-to-quadrants.md`: без честных границ нельзя назначать компонентам разный уровень.

## 3) Что из Agent1st не берём и почему

- **Роли и права агента, «право не согласиться».** Свойство процесса, в продукте не наблюдаемо.
- **Формат жалобы, формат передачи.** Инструменты процесса.
- **Запрет на пошаговые инструкции для сильного агента.** Здесь есть напряжение с самим исследованием: таблица из 38 критериев выглядит как длинная инструкция. Снимается тем, что критерии это утверждения о продукте, проверяемые машиной или ревьюером, а не шаги для исполнителя. Но напряжение стоит помнить: если список превратится в инструкцию агенту, он будет работать против Attention Engineering.

## 4) Что исследование добавляет к Agent1st (обратное направление, для памяти)

Пока только запись, не предложение менять протокол:
- Agent1st не говорит о safety, цепочке поставок, тестах качества тестов, эксплуатируемости, стабильности поставки. Это свойства результата, а протокол о маршруте.
- Двухслойная модель «единая база плюс надстройка по риску» в Agent1st отсутствует.

## 6) Источники

Понимание и имена
- Lawrie, Morrell, Feild, Binkley, «Effective Identifier Names for Comprehension and Memory» (2007) — https://www.cs.kent.edu/~jmaletic/cs63902/Papers/Lawrie07.pdf — established, более 100 программистов.
- Эксперимент с профессиональными разработчиками: полные слова улучшают поиск дефектов — Empirical Software Engineering, DOI 10.1007/s10664-018-9621-x — supported.
- Похожие имена ведут к недопониманию — https://arxiv.org/pdf/2507.18081v1 — hypothesis, разведочное исследование 2025.

Мёртвый код и неиспользуемые функции
- Romano et al., «A Multi Study Investigation into Dead Code», TSE 2018 — https://mustang.cec.miamioh.edu/Resources/Publication/TSE18-DeadCode.pdf — supported, интервью и четыре эксперимента с репликами.
- Неиспользуемые функции в промышленных системах (28–45%) — https://teamscale.com/hubfs/26978363/Publications/2020-unnecessary-code-tosem.pdf — supported.

Обработка исключений
- «Studying the relationship between exception handling practices and post-release defects», MSR 2018 — https://2018.msrconf.org/event/msr-2018-papers-studying-the-relationship-between-exception-handling-practices-and-post-release-defects — supported; вывод про Dummy Handler и Generic Catch через пересказ https://neverworkintheory.org/2021/09/16/exception-handling-practices-and-post-release-defects.html .
- «Studying the Prevalence of Exception Handling Anti-Patterns» — https://arxiv.org/pdf/1704.00778 — supported, 16 проектов.
- Запахи обработки исключений как баги надёжности (124 из 357) — https://jit.ndhu.edu.tw/article/view/1781 — supported, один проект.

Устаревшие комментарии
- «Investigating the Impact of Code Comment Inconsistency on Bug Introducing» (2024) — https://arxiv.org/abs/2409.10781 — supported, эффект 1,5× с затуханием во времени.
- Wen et al., ко-эволюция кода и комментариев (2019) — https://www.inf.usi.ch/faculty/lanza/PUBS/P/Wen2019a.pdf — supported.
- Tan et al. (iComment), Fluri et al. — по пересказу в работе 2024 года — established для связи «необновлённый комментарий → будущий баг».

Agent1st
- `AGENTS.md`, `docs/FOUNDATIONS.md` этого репозитория — практика проекта; исследовательские основания для Attention Engineering (Lost in the Middle, Context Rot) приведены там.
