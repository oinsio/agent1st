# Калибровка определения на SQLite

**Статус:** вторая проба определения из `definition.md` после `calibration-curl.md`. SQLite выбран как проект, который сам документирует свою стратегию тестирования и считается одним из самых проверенных программ в мире: авиационный стандарт покрытия, миллиарды установок, формат файла стабилен с 2004 года.

**Источники фактов:** зеркало `github.com/sqlite/sqlite`, коммит `d7e0a47` (2026-10-18), глубина 300 коммитов; страница `sqlite.org/testing.html` (цифры на ней от версии 3.42.0, 2023). Канонический репозиторий Fossil, не Git.

Шкала та же, что в curl, плюс два маркера: **(вне репо)** артефакт публичен, но живёт не в репозитории; **(приватно)** артефакт существует, но недоступен никому, кроме авторов.

## 3) Что SQLite делает, а определение не видит

- **Покрытие как цель, а не как побочный показатель.** 100% ветвей и MC/DC. В определении нет критерия покрытия вообще, только Н7 «прочитано или покрыто» без порога.
- **Соотношение тестов к коду** 590:1. Определение не спрашивает, сколько доказательств по сравнению с кодом.
- **Эквивалентность сборок:** тесты гоняются с оптимизацией и без, вывод обязан совпасть. Это проверка компилятора и неопределённого поведения, которой нет ни в одном пункте.
- **Целостность поставки:** `manifest.uuid`, раздел «Verifying Code Authenticity», аффидавиты. Свойство Д защищает от чужих секретов и зависимостей, но не требует, чтобы пользователь мог проверить подлинность самого продукта.
- **Чеклист релиза на ~200 пунктов, не автоматизирован.** Прямо противоречит правилу базы «дёшев, автоматизируем». Самый проверенный проект держит ручной чеклист как основной релизный артефакт.
- **Напряжение между MC/DC и фаззингом** признано авторами: код с полным покрытием ветвей уязвимее для фаззинга. Определение считает виды доказательств независимыми и суммируемыми.
- **Отказ от ИИ-кода как политика качества.** Для определения, написанного под ИИ-разработку, это внешняя точка отсчёта: проект с лучшим тестированием в мире выбрал запрет, а не учёт.

## 4) Выводы для определения

1. **Новая ось: кому доказано.** TH3, dbsqlfuzz, мутационный прогон, чеклист релиза существуют, но приватны. Определение говорит «доказано артефактами» и молчит о том, кто может их увидеть. Для заказной разработки артефакты должен видеть заказчик. Для продукта пользователь видит только послужной список. Нужно ввести три уровня: доказано себе, заказчику, публике.
2. **Определение переобучено на GitHub-процесс.** Шесть пунктов требуют «лог CI» или «конфиг CI». SQLite без публичного CI проваливает их, прогоняя при этом 248 миллионов тестов перед релизом. Проверка должна формулироваться через факт прогона до доставки пользователю, а не через место, где он записан.
3. **Каденция «на каждый push» не базовая.** SQLite делает тяжёлые проверки перед релизом, лёгкие на коммит. Б19 и аналогичные пункты должны говорить «до того, как изменение достигнет пользователя».
4. **Шесть пунктов провалены обоими проектами:** Б1, Б8, Б12, Б13, Б16, Б17. Это сильнейший сигнал калибровки. Два признанных проекта не делают того, что определение называет обязательным для каждой строки кода.
5. **Ядро подтверждено обоими проектами:** Б3, Б4, Б9, Б14 и Н4, Н12, Н16. Эти пункты измеряют то, что хорошие проекты действительно делают.
6. **Б19 как база под сомнением.** curl держит CodeQL на каждый push, SQLite считает статанализ бесполезным и гоняет санитайзеры перед релизом. Оба правы для своего кода. Пункт лучше перевести в «динамические проверки памяти и UB до релиза», а SAST оставить рекомендацией.
7. **Н1 оказалось различителем.** Мутационное тестирование есть у SQLite и нет у curl. Оба имеют внешнего адресата, по правилу Н1 оба обязаны. Либо curl не проходит надстройку, либо правило Н1 слишком широкое. Фаззинг у curl выполняет ту же роль, и определение должно это признать: мутации или фаззинг, по типу кода.
8. **Правило базы «дёшев, автоматизируем» опровергнуто практикой.** Ручной чеклист на 200 пунктов у SQLite и ручная политика зависимостей у curl. Критерий включения в базу нужно заменить: «без этого дефект доходит до пользователя незамеченным».

## 5) Ограничения

- Половина доказательств SQLite приватна; вердикты по ним опираются на описание авторов, не на проверку.
- Цифры testing.html от 2023 года.
- Оба откалиброванных проекта: библиотека плюс CLI на C, без сервиса, без UI, без хранимых чужих данных в проде. Свойство Г до сих пор не откалибровано. Третий кандидат обязан быть сервисом.
