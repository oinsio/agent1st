# Внешняя проба определения v3.0 на LiteLLM: без чтения дерева

**Статус:** одиннадцатая проба, вторая по версии 3.0, неполная по замыслу. Дерево репозитория не читалось и не исполнялось: сопровождающий остановил клон и запретил связываться с кодом проекта, у которого в марте 2026 была закладка в опубликованных версиях. Факты взяты только из внешних источников. Записана 2026-10-19.

**Зачем всё же записывать.** LiteLLM это отрицательный контроль нового типа: проект с 31 опубликованной уязвимостью за полтора года и с инцидентом поставки. Вопрос пробы: назвало бы определение заранее те критерии, по которым проект провалился, и что из этого видно принимающему снаружи, без доступа к дереву. Это также первая проба типа «под нагрузкой» и компонента, который вызывает LLM и аутентифицирует пользователей.

**Что это:** `BerriAI/litellm`, шлюз к ста с лишним провайдерам LLM: библиотека Python и прокси-сервер с ключами, командами, бюджетами, базой PostgreSQL, Redis, журналом трат и интерфейсом администратора. 61 564 звезды, лицензия нестандартная (`NOASSERTION` по GitHub), текущая версия на PyPI 1.106.0 от 2026-10-18, колёса собираются под `cp310-abi3`, то есть в пакете есть скомпилированный код.

**Источники:** GitHub API без авторизации (лимит 60 запросов в час, исчерпан на пятой странице): 17 advisories репозитория, 31 запись глобальной базы по пакету `litellm`, 100 последних коммитов `main`, правила ветки `main`, ревью на четырёх запросах, список из 39 имён workflows; PyPI JSON и провенанс восьми файлов релиза 1.106.0; OpenSSF Scorecard от 2026-10-19; семь страниц `docs.litellm.ai` (здоровье, прод, логирование, база, ключи, релизы, развёртывание), прочитанные агентом. Ни один файл репозитория не открывался.

**Профиль и уровень:** самостоятельный хостинг плюс продуктовый (LiteLLM Cloud упоминается в документации; здесь оценён только видимый из репозитория профиль). Внешний адресат. Релиз необратим: миграции `prisma migrate deploy` выполняются при старте, процедуры отката в документации нет. Тип: хранит данные (ключи, пользователи, журнал трат с промптами по настройке), работает непрерывно, вызывает LLM с действиями (MCP, инструменты, guardrails с исполнением кода), парсит внешний ввод, под нагрузкой (документация задаёт число воркеров, Redis «как только экземпляров больше одного», пул соединений по формуле, режим выше 1000 RPS). Включается вся надстройка. Код агента: 16 из 100 коммитов внесены ботом `devin-ai-integration`, компенсация обязательна.

**Не подключено к обвязке (§9 п.8), насколько видно снаружи:** правило ветки требует четыре проверки: `lint passed`, `smoke passed`, `unit passed`, `cost-map-guard`. Workflows `mutation-test`, `codspeed`, `test-e2e-redis-chaos`, `weekly_load_anomaly`, `e2e_record_replay`, `osv-scan`, `image-scan`, `codeql`, `scorecard`, `zizmor` в обязательных проверках не значатся: по именам это сильные артефакты, но их результат на слияние не влияет. Внутреннее устройство workflows не читалось, и утверждать, что они не валят сборку иначе, нельзя.

Шкала §3: ДА / ЧАСТИЧНО / НЕТ / Н/П; «не проверено» там, где нужен файл из дерева.

## 1) Опубликованные уязвимости как отрицательный контроль

31 запись с марта 2025 по сентябрь 2026, из них 6 критических. Каждая отнесена к критерию определения, чьё утверждение она нарушает. Если критерий назван, определение требовало доказательства именно этого до поставки.

|---|---|---|

| Повышение привилегий | эскалация до админа через повторное использование salt key между доменами (крит.), конфигурационная конечная точка без ограничений, пользователь меняет свою роль через `/user/update`, internal_user создаёт ключи шире своих прав, internal_user_viewer читает файлы через `vertex_ai_credentials` | Я20: для каждого пути к данным тест, что чужой получает отказ |

**Вывод контроля.** Все 31 запись ложатся на семь критериев: Я20, Н24, Н25, Н22, Н20, Я6 (ветвь «модель с действиями»), Н19, плюс среда С1/С4/С6 для инцидента поставки. Ни одна не потребовала критерия, которого в определении нет. Три из семи критериев, Н24, Н25 и Н19, добавлены в версии 2.1 по сверке с OWASP и прогону кандидатов; эта проба подтверждает их задним числом на живом проекте. Повторяемость классов (три SSRF за год, две SSTI в одной конечной точке, восемь обходов аутентификации) говорит, что исправления закрывали экземпляр, а не класс: Н26 требует реестр с привязкой класса угрозы к проверке, и отсутствие такого реестра видно по самой истории.

## 3) Что это говорит об определении

1. **Определение предсказывает классы инцидентов LiteLLM целиком.** 31 запись легла на семь критериев и среду. Это сильнее, чем `negative-control-incidents.md`: там инциденты подбирались под критерии, здесь список задан проектом. Особенно подтверждена формулировка Я20 про исходящий запрос по адресу из ввода: три SSRF подряд.

2. **Повтор класса это сигнал на Н26, видимый без дерева.** Если один класс уязвимости закрывается дважды и трижды, реестра угроз с привязкой к проверке нет. Кандидат в строку Н26 как замена для оценки снаружи: «повторная публикация уязвимости того же класса опровергает утверждение Н26».

3. **Бот-штамп обходит правило «одно одобрение».** `litellm-stampbot` ставит одобрение, которого требует правило ветки. К1 называет это штампом, но строка К1 говорит о человеческом коммите по отчёту агента. Нужна явная фраза: одобрение, поставленное учётной записью, которую контролирует та же сторона, что и автор, не закрывает требование второго читателя (Н9) и не является границей (К1). Scorecard этот штамп не видит и даёт 9/10.

4. **Н20 после инцидента поставки.** Проект пережил публикацию вредоносных версий и через семь месяцев не внедрил провенанс. Определение ставит НЕТ по факту, и это правильный вердикт: репутация и число звёзд в критерий не входят (память проекта: определение для создания, не для поиска).

5. **Правило 2 на проверке живости.** `allow_requests_on_db_unavailable` превращает readiness в безусловный 200. Документация это честно записывает, но для принимающего это переключатель, отключающий проверку одной строкой конфигурации; строка Н15 про «маршрут, который не опрашивает ни образ, ни оркестратор» это не покрывает, нужна отсылка к правилу 2.

6. **Внешняя проба даёт вердикты для 23 критериев из 61.** Этого хватает на свойства Д и частично Г, но не на А, В и компенсацию. Для отрицательного контроля этого достаточно; для калибровки планки нет. Формат «внешняя проба» стоит признать отдельным видом записи: когда дерево читать нельзя, записываются только критерии, у которых доказательство публично вне репозитория (правило 4), и инциденты как опровержения.

7. **Умолчания, исправленные релизом.** Я17 требует, чтобы небезопасное умолчание отвергалось тестом. У LiteLLM умолчания становятся безопасными релизами после уязвимостей (stdio MCP выключен по умолчанию с 1.104.0). История релизов, в которой умолчание меняется после advisory, это публичный след нарушения Я17, видимый без дерева.

## 4) Ограничения

- Дерево не читалось: вердикты «не проверено» это не НЕТ. Для 38 критериев факта нет.
- GitHub API без авторизации: ревью проверены на четырёх запросах, список workflows известен только по именам.
- Scorecard взят как сторонняя сводка; его методика отличается от определения (пример: Code-Review 9/10 при одобрении ботом).
- Документация прочитана агентом по семи страницам; страницы пользователей и руководства по обновлению не открылись.
- Профиль продукта (LiteLLM Cloud) не оценивался.
- Advisory не читались целиком, классификация по заголовкам и кратким описаниям.
